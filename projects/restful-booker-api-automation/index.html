01 Context

Project Context

This is an independent, public QA automation project built to show how I structure and run API tests. The target is the RESTful Booker API, a public booking system designed for API testing practice.

The project prioritizes code quality, maintainability, and clarity. It demonstrates how to design reusable API clients, organize test suites effectively, and structure meaningful test coverage rather than simply increasing test count.

06 Strategy

Testing Strategy

Status Code Validation

22 of the 47 tests assert a status code. These are all the codes asserted, by request, with the number of tests that assert each:

  • GET /ping: 201 (1 test)
  • POST /auth: 200 (3 tests)
  • POST /booking: 200 (1 test), 500 (2 tests)
  • GET /booking/{id}: 404 (6 tests)
  • PUT /booking/{id}: 400 (1 test), 403 (2 tests), 405 (1 test)
  • PATCH /booking/{id}: 403 (1 test)
  • DELETE /booking/{id}: 403 (2 tests), 405 (2 tests)

No test asserts a 401. The status of a successful create, update, patch or delete is not asserted either, because the client helpers that return a parsed body do not check it. The 200 on POST /auth is a failed login (the body carries a reason), and the 500 is a booking missing a required field.

Response Structure

Validate JSON payload structure, data types, and required fields

Data Integrity

Validate API behavior with invalid inputs, edge cases, and error scenarios

07 Architecture

Framework Architecture

The layout of the repository at the pinned commit (a385240): client classes, models and test data under src/api, and one spec file per area under tests/api.

src/api/ ├── clients/ │ ├── api-client.ts (base class) │ ├── auth-client.ts │ └── booking-client.ts ├── models/ │ └── booking.types.ts ├── test-data/ │ └── booking-data.ts └── config.ts tests/api/ ├── auth.spec.ts ├── booking-create.spec.ts ├── booking-delete.spec.ts ├── booking-partial-update.spec.ts ├── booking-read.spec.ts ├── booking-update.spec.ts ├── health-check.spec.ts ├── negative-testing.spec.ts └── workflow.spec.ts playwright.config.ts .github/workflows/playwright.yml

Key Design Principles:

  • ✓ Reusable API Clients — A base APIClient holds the HTTP calls and headers; AuthClient and BookingClient add one named method per endpoint. Four tests send a raw request instead: the health check, two malformed booking IDs and a PATCH without a token.
  • ✓ TypeScript Interfaces — booking.types.ts defines interfaces for a booking and the two responses, which type the test data and the client methods. They are checked at compile time only; nothing validates a response against them at run time.
  • ✓ Centralized Test Data — src/api/test-data/booking-data.ts exports four sample bookings. The specs use three of them (validBooking, updatedBooking and bookingWithoutAdditionalNeeds); validBooking2 is not used. There are no Playwright fixtures: each test creates its own bookings.
  • ✓ Clean Test Organization — One spec file per operation (create, read, update, partial update, delete), plus health check, authentication, negative cases and workflows: nine files under tests/api.
  • ✓ Assertions — Status codes (22 of the 47 tests), response fields and a read-back after writes. Three negative tests cannot fail and the delete test checks only that the reply is truthy (see Negative Testing below).

08 Negative tests

Negative Testing

The test suite includes 8 negative tests, covering these areas:

  • Invalid Credentials
  • Invalid IDs
  • Invalid Inputs
  • Missing Fields
  • Edge Cases

Two of the eight assert a rejection (an incomplete PUT returns 400, a non-numeric ID returns 404). The other six record input this practice API accepts: zero and negative prices, an invalid date, a checkout before the check-in, special characters in the login and a 1,000-character name. Three of those six use expect(response.ok).toBeTruthy() without calling ok(), so the assertion cannot fail. The article explains what I would change.
