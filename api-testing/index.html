Ten risks I check on any API. For each one: the tests in my public repositories that cover it, whether they run in CI, the exact lines at a pinned commit, and where the coverage is weak or missing.

What this page is

The evidence comes from three independent public projects, not from employer work: a TypeScript suite for the RESTful Booker practice API, a JavaScript suite for the Automation Exercise demo shop (API and web pages), and the API and security tests of a Razorpay Test Mode checkout app that I built as the test target. The targets are practice APIs and a payment sandbox. None of them is a client system.

I gave every API test in those repositories one risk category: all 47 tests in RESTful Booker, 32 of the 37 in Razorpay (the other five check the checkout page) and 16 of the 26 in Automation Exercise (the other ten drive the shop's web pages). The table shows where they sit. It is my tagging, and a count says how many tests touch a risk, not how well they test it.

What I check on any API

Each item links to its block in the evidence map below.

  • Authentication

    Can a caller prove who it is, and does a missing or wrong credential fail in a way no client could mistake for success?

  • Authorization

    Once a caller is known, can it reach only what it is allowed to? A valid token is not the same as permission for this record.

  • Status codes

    Does each outcome return the code the API documents, and does the test assert that code instead of assuming success?

  • Response structure

    Are the fields and types a client depends on present, and are fields that must stay private, such as secrets, absent?

  • Invalid input

    What happens with missing, malformed, out-of-range or oversized input: a clear rejection, silent acceptance, or a server error?

  • CRUD lifecycle

    Do create, read, update and delete work in sequence, the way a real client would use them?

  • Read-back after write

    After a change, does a separate read show it, rather than trusting the response to the write itself?

  • Idempotency and replay

    What happens when the same request arrives twice, from a retry, a double click or a redelivered webhook?

  • Signature and HMAC

    Does the server accept a correctly signed message and reject one that is unsigned, wrongly signed or changed after signing?

  • Error handling

    Do failures return a controlled message without internal details, and does the service keep working afterwards?

Evidence map

One block per risk. Each names the tests that cover it, links every test to its lines at the pinned commit, shows a short excerpt copied from the repository, and says what is weak or missing. Razorpay tests are named by their IDs; the other two repositories have no IDs, so their tests are named by file and line range. A badge describes one test or one gap:

  • Runs in CI The repository's own GitHub Actions workflow runs it. That says nothing about how strong it is.
  • Live gateway only It needs my original Razorpay Test Mode account, so CI never runs it.
  • Partly tested Some of the risk is covered; the gap is stated next to it.
  • Not tested No test in these repositories covers it. I say what I would test instead.
  • Assertion cannot fail The test passes whatever the API returns, so it proves nothing.

Authentication

Partly tested What I verify: a valid login returns a usable credential, and a failed login is reported as a failure, not as a success.

  • Runs in CI RESTful Booker · auth.spec.ts:14–20 (opens in a new tab): valid credentials return a token made of hex characters.
  • Runs in CI RESTful Booker · auth.spec.ts:28–35 (opens in a new tab): wrong credentials return HTTP 200 with a reason field and no token. The test pins that behaviour; the article says why I would raise it.
  • Runs in CI Automation Exercise · authentication.api.spec.js:46–68 (opens in a new tab): wrong credentials return HTTP 200 with responseCode 404 and “User not found!” in the body.
  • Runs in CI Automation Exercise · authentication.api.spec.js:6–44 (opens in a new tab): a valid login. It needs an existing account passed in as repository secrets (workflow, lines 70–79 (opens in a new tab)), so it cannot pass from a clean clone.
  • Not tested Expired and revoked tokens, lockout or rate limiting after repeated failures, and malformed credential headers. On a real API I would test each of those.

Weak: auth.spec.ts:45–51 (opens in a new tab) only checks that two tokens are truthy.

Authorization

Partly tested What I verify: a caller can change only what it is allowed to change, and a missing or wrong token is refused.

  • Runs in CI RESTful Booker · booking-update.spec.ts:40–44 (opens in a new tab) and booking-update.spec.ts:46–50 (opens in a new tab): PUT without a token, or with an invalid one, returns 403.
  • Runs in CI RESTful Booker · booking-partial-update.spec.ts:74–82 (opens in a new tab): PATCH without a token returns 403.
  • Runs in CI RESTful Booker · booking-delete.spec.ts:38–44 (opens in a new tab) and booking-delete.spec.ts:46–52 (opens in a new tab): DELETE without a token, or with an invalid one, returns 403.
  • Not tested Roles. RESTful Booker has one admin account and a token that is either present or not, so nothing here shows that one user cannot change another user's booking, or that a lower role cannot do what an admin can.
  • Not tested Automation Exercise · the suite reads an account's details with nothing but its email address (AccountApi.js, lines 22–32 (opens in a new tab), used by account.api.spec.js:17–62 (opens in a new tab)). It uses that as a working feature and never tests who else should be allowed to do it.

What I would test: two accounts, each trying to read and change the other's data; every role against every endpoint; a token issued for one resource used on another.

Status codes

Runs in CI What I verify: each outcome returns the documented code, and the test asserts the code instead of assuming success.

  • Runs in CI RESTful Booker · booking-read.spec.ts:53–57 (opens in a new tab) and booking-read.spec.ts:59–63 (opens in a new tab): an unknown ID and a non-numeric ID return 404.
  • Runs in CI RESTful Booker · health-check.spec.ts:5–12 (opens in a new tab): GET /ping returns 201 with the body “Created”.
  • Partly tested RESTful Booker · booking-update.spec.ts:59–63 (opens in a new tab) and booking-delete.spec.ts:54–57 (opens in a new tab): PUT and DELETE on a booking that does not exist return 405. The tests record what the API does, but their titles (“should return 405”) read as if 405 were the right answer. I would expect 404.
  • Runs in CI Automation Exercise · products.api.spec.js:127–176 (opens in a new tab) and authentication.api.spec.js:125–149 (opens in a new tab): an unsupported method is answered with HTTP 200 and responseCode 405 in the body. Each test asserts both numbers, because a client that checks only the HTTP status would treat these errors as success.
  • Not tested Headers that belong with a status, such as Allow on a 405 or Retry-After on a 429, and the codes for rate limiting and server errors. I would assert the header together with the code, and on an API that rate-limits I would trigger the limit on purpose.

Response structure

Partly tested What I verify: the fields and types a client relies on are present, and fields that must stay private are absent.

  • Runs in CI RESTful Booker · booking-create.spec.ts:34–40 (opens in a new tab): numeric and boolean fields keep their types.
  • Runs in CI RESTful Booker · booking-read.spec.ts:27–35 (opens in a new tab): the booking has five named fields. It checks only that they exist, not their types.
  • Runs in CI RESTful Booker · booking-create.spec.ts:24–32 (opens in a new tab) and booking-update.spec.ts:52–57 (opens in a new tab): compare a whole booking with toEqual, which would also fail on an extra or renamed field in those two responses.
  • Runs in CI Automation Exercise · products.api.spec.js:81–121 (opens in a new tab): the brands list is a non-empty array whose first item has id and brand.
  • Runs in CI Razorpay · CONFIG-001 (health.spec.js:16–26) (opens in a new tab) and CONFIG-002 (health.spec.js:28–45) (opens in a new tab): the public config has keyId, currency and a boolean configured, and its JSON contains none of the strings keySecret, webhookSecret or RAZORPAY.
  • Assertion cannot fail Razorpay · ORDER-001 (orders.spec.js:39–66) (opens in a new tab): every check sits inside if (status === 200) or else if (status === 503). With the placeholder keys CI uses, the route returns 400 (payments.js, lines 132–138 (opens in a new tab)), so in CI no assertion runs. I confirmed the 400 by calling the endpoint with the CI configuration on 22 October 2026.
  • Not tested Schema or contract validation. Nothing checks a response against a schema, so outside the two toEqual checks a renamed, retyped or extra field would pass. I would validate each response against the API's published schema, including required fields and types.

Invalid input

Partly tested What I verify: bad input is rejected with a clear client error, not accepted silently or answered with a server error.

  • Runs in CI RESTful Booker · negative-testing.spec.ts:64–75 (opens in a new tab) and negative-testing.spec.ts:77–80 (opens in a new tab): an incomplete PUT returns 400 and a non-numeric booking ID returns 404. Only these two of the eight tests in negative-testing.spec.ts assert a rejection.
  • Assertion cannot fail RESTful Booker · negative-testing.spec.ts:28–36 (opens in a new tab), negative-testing.spec.ts:38–49 (opens in a new tab) and negative-testing.spec.ts:51–62 (opens in a new tab): a negative price, an invalid date and a checkout before check-in. Each ends with expect(response.ok).toBeTruthy() (lines 35, 48 and 61). ok is a method; without the call the assertion only checks that the method exists, so it passes whatever the API returns.
  • Runs in CI RESTful Booker · negative-testing.spec.ts:18–26 (opens in a new tab) and negative-testing.spec.ts:87–99 (opens in a new tab): a zero price and a 1,000-character first name are accepted. Like the rest of that file, they record what the practice API accepts; they do not show it rejecting anything.
  • Runs in CI RESTful Booker · booking-create.spec.ts:56–70 (opens in a new tab) and booking-create.spec.ts:72–83 (opens in a new tab): a booking without firstname or without bookingdates returns 500. The tests pass because the API answers with a server error, which I would report rather than assert as correct.
  • Runs in CI Razorpay · SIG-004 (signature-verification.spec.js:120–133) (opens in a new tab), SIG-005 (signature-verification.spec.js:135–150) (opens in a new tab), SIG-006 (signature-verification.spec.js:152–167) (opens in a new tab), WEB-004 (webhook-validation.spec.js:106–124) (opens in a new tab), ERR-004 (error-handling.spec.js:58–76) (opens in a new tab) and REF-001 (error-handling.spec.js:82–94) (opens in a new tab): missing fields, a missing event-ID header and malformed JSON return 400.
  • Runs in CI Automation Exercise · account.api.spec.js:238–315 (opens in a new tab), account.api.spec.js:321–397 (opens in a new tab), account.api.spec.js:402–481 (opens in a new tab), authentication.api.spec.js:69–95 (opens in a new tab), authentication.api.spec.js:97–123 (opens in a new tab) and products.api.spec.js:55–79 (opens in a new tab): missing parameters and a duplicate email return responseCode 400 inside an HTTP 200.
  • Assertion cannot fail Razorpay · ORDER-003 (orders.spec.js:26–37) (opens in a new tab): a client-supplied amount must not change the order amount. Its assertions run only when order creation returns 200, which it does not in CI (excerpt below).
  • Not tested Boundary values, wrong types (a string where a number belongs), unknown fields, very large bodies and injection-style strings, each with an assertion on the rejection and its error message.

CRUD lifecycle

Runs in CI What I verify: create, read, update and delete work in sequence, as one flow a client would follow.

  • Runs in CI RESTful Booker · workflow.spec.ts:10–47 (opens in a new tab): authenticate, create, read, update, read again, delete, and confirm the booking is gone.
  • Runs in CI RESTful Booker · workflow.spec.ts:49–84 (opens in a new tab): create two bookings, find both in the list, update and delete one, and confirm the other still exists.
  • Runs in CI RESTful Booker · workflow.spec.ts:86–111 (opens in a new tab): create, change one field with PATCH, and confirm the other fields kept their values.
  • Runs in CI Automation Exercise · account.api.spec.js:17–62 (opens in a new tab): a fixture creates a fresh account, the test reads it back by email, and the fixture deletes it afterwards.
  • Partly tested RESTful Booker · cleanup. The workflow tests delete their bookings only after their other assertions, so a failed assertion earlier in the test skips the delete. Only six of the 47 tests delete a booking at all.
  • Not tested Two clients updating the same record at once, and filtering or paging the list. I would update one record from two sessions and check which write wins and what each response says, and request a filtered, paged list and check its contents against what I created.

Read-back after write

Runs in CI What I verify: after a write, a separate read shows the change, instead of trusting the write's own response.

  • Runs in CI RESTful Booker · booking-update.spec.ts:32–38 (opens in a new tab) and booking-partial-update.spec.ts:63–72 (opens in a new tab): after PUT or PATCH, a GET returns the new values.
  • Runs in CI RESTful Booker · booking-delete.spec.ts:28–36 (opens in a new tab): after DELETE, a GET returns 404.
  • Runs in CI Automation Exercise · account.api.spec.js:69–153 (opens in a new tab) and account.api.spec.js:160–231 (opens in a new tab): after an update the account shows the new company, address and city; after a delete it is reported as not found.
  • Runs in CI Razorpay · WEB-FIX-001 (webhook-validation.spec.js:259–286) (opens in a new tab) and WEB-FIX-002 (webhook-validation.spec.js:288–314) (opens in a new tab): the order is read back after a webhook: paid after a valid one, still created after a rejected one. Both seed their order by importing the app's own database module (webhook-validation.spec.js, lines 237–239 (opens in a new tab)), so they need the app running locally on the same database file (db.js, lines 13–14 (opens in a new tab)).
  • Partly tested RESTful Booker · booking-delete.spec.ts:20–26 (opens in a new tab): the delete test asserts only that the response body is truthy. A rejected delete returns 403 with the body “Forbidden”, which is also truthy; I checked that body on 22 October 2026. The read-back test above would still catch a delete that did nothing.

Idempotency and replay

Partly tested What I verify: sending the same request twice does not create a second effect or corrupt state.

  • Runs in CI Razorpay · WEB-005 (webhook-validation.spec.js:126–158) (opens in a new tab) and WEB-FIX-004 (webhook-validation.spec.js:336–362) (opens in a new tab): the same signed webhook event sent twice is processed once; WEB-FIX-004 also reads the order back to show the second delivery changed nothing.
  • Runs in CI Razorpay · WEB-006 (webhook-validation.spec.js:160–199) (opens in a new tab): two different event IDs are both processed.
  • Live gateway only Razorpay · REPLAY-001 (signature-verification.spec.js:58–80) (opens in a new tab): verifying the same real payment twice leaves the order paid with the same payment ID. It needs my original Test Mode account, so CI never runs it.
  • Runs in CI RESTful Booker · booking-delete.spec.ts:59–67 (opens in a new tab): a second DELETE of the same booking returns 405.
  • Not tested Two identical requests in flight at the same moment, and idempotency keys on create requests. I would send concurrent duplicates and check that exactly one record or charge results.

Signature and HMAC

Partly tested What I verify: a correctly signed message is accepted, and an unsigned, wrongly signed or modified one is rejected.

  • Runs in CI Razorpay · WEB-001 (webhook-validation.spec.js:42–65) (opens in a new tab) and WEB-FIX-001 (webhook-validation.spec.js:259–286) (opens in a new tab): a webhook signed over its exact raw body is accepted.
  • Runs in CI Razorpay · WEB-002 (webhook-validation.spec.js:67–85) (opens in a new tab), WEB-003 (webhook-validation.spec.js:87–104) (opens in a new tab), WEB-007 (webhook-validation.spec.js:201–223) (opens in a new tab), WEB-FIX-002 (webhook-validation.spec.js:288–314) (opens in a new tab) and WEB-FIX-003 (webhook-validation.spec.js:316–334) (opens in a new tab): a wrong signature, a missing signature header, or a body changed after signing is rejected with 401.
  • Runs in CI Razorpay · SIG-002 (signature-verification.spec.js:82–99) (opens in a new tab) and SIG-003 (signature-verification.spec.js:101–118) (opens in a new tab): payment verification rejects a wrong signature and a signature made for a different order ID.
  • Live gateway only Razorpay · SIG-001 (signature-verification.spec.js:37–56) (opens in a new tab): payment verification accepts a correct signature for a real captured payment. It needs the original Test Mode account and that payment, so in CI payment verification is only tested for rejections, never for acceptance.
  • Not tested A signature made with an old or rotated secret, and a signature header of the wrong length or encoding. I would send each and expect a 401, not a server error.

Error handling

Partly tested What I verify: failures return a controlled message with no internal details, and the service keeps working afterwards.

  • Runs in CI Razorpay · ERR-002 (error-handling.spec.js:26–46) (opens in a new tab): a failed verification returns 401, and the body contains no stack-trace or file-path text.
  • Runs in CI Razorpay · ERR-003 (error-handling.spec.js:48–56) (opens in a new tab): an unknown route returns a JSON 404 that names the path.
  • Runs in CI Razorpay · REF-ERR-001 (refund-error-handling.spec.js:16–32) (opens in a new tab) and REF-ERR-002 (refund-error-handling.spec.js:34–49) (opens in a new tab): a refund the gateway rejects returns a controlled 400 or 404, and the server keeps answering. They make a real call to Razorpay's API, so they need network access; I have not traced which rejection CI receives.
  • Runs in CI Razorpay · ERR-001 (error-handling.spec.js:4–24) (opens in a new tab) and ORDER-002 (orders.spec.js:4–24) (opens in a new tab): a failed order creation hides gateway details. ERR-001 checks only when the status is not 200, and ORDER-002 accepts 200, 400 or 503; with the CI configuration both get 400, so their checks do run.
  • Not tested A slow or failing dependency, 5xx bodies, and the error bodies of RESTful Booker and Automation Exercise. I would simulate the dependency failing and assert the status, the message, and that nothing was half-written.

How I structure Playwright API suites

API client classes

Requests go through client classes, not inline calls. In RESTful Booker a base class builds the URL and headers, and one class per resource gives each call a name, so a test reads bookingClient.createBooking(validBooking) and a header change is made in one place. Automation Exercise uses the same idea in plain JavaScript, one class per area (AccountApi.js (opens in a new tab)).

Raw responses and parsed bodies

Each HTTP verb has two helpers. The parsed ones return the body; the …Response ones return the raw response, so a test can assert the status. The weakness is that the parsed helpers never look at the status. The delete helper below returns the text of any reply, so a 403 comes back as the string “Forbidden”, and that is why the truthy check in the delete test proves nothing. The article walks through the same split for get.

Data for each test

Each test creates the data it needs instead of sharing records. In Automation Exercise a fixture generates a unique account, creates it through the API, hands it to the test and deletes it in its teardown, which Playwright runs even when the test fails. RESTful Booker creates a booking per test, but its read, update and partial-update files do it in beforeEach and never delete it. The Razorpay webhook tests that expect an event to be accepted build a unique event ID with Date.now(), because processed IDs are stored and a fixed ID would be “already processed” on the next run (webhook-validation.spec.js, lines 43–47 (opens in a new tab)).

Read back after every write

A write's own response says what the server claims to have done; a separate GET says what it stored. I treat the second as the evidence. The read-back block above lists where these repositories do it, and the delete test shows what happens when a test trusts the write alone.

Retries, workers and traces

Each setting changes how much a green run means. RESTful Booker allows one retry in CI and runs one worker there (playwright.config.ts, lines 7–8 (opens in a new tab)). Razorpay allows two retries in CI with one worker, and its CI command runs Chromium only and leaves out the live tests (playwright.config.js, lines 7–8 (opens in a new tab); package.json, line 13 (opens in a new tab)). Automation Exercise allows one retry everywhere, not only in CI. All three keep a trace only on the first retry, so a run that needed no retry leaves no trace to open. A test that fails and then passes on retry still counts as passed, so I read a green run together with its retry setting.

What this does not prove

All of this is true of the published code at the commits above.

  • No schema or contract validation. Responses are checked field by field, and four assertions in RESTful Booker compare a whole booking with toEqual. Nothing validates a response against a schema.
  • No performance or load testing. None of the three repositories asserts a response time or sends load.
  • No role-based authorization. The only access control tested is a token being present, absent or invalid. No test uses more than one role, or one user's token on another user's data.
  • Cleanup is missing in most RESTful Booker tests. Only six of the 47 delete what they create, so the suite leaves bookings on a shared public service.
  • Some tests cannot fail. Three RESTful Booker negative tests (lines 35, 48 and 61 of negative-testing.spec.ts) pass whatever the API returns, and Razorpay's ORDER-001 and ORDER-003 run no assertions in CI. The counts on this page include them.
  • Payment verification is never accepted in CI. SIG-001 and REPLAY-001 need my original Razorpay Test Mode account, so CI only tests that payment verification rejects bad input.
  • Practice APIs and a sandbox only. RESTful Booker and Automation Exercise are public services that other people also use, and their behaviour and uptime are outside my control. The Razorpay tests run against my own app in Test Mode, so a defect found there is a bug in my code, not in Razorpay. None of it is a production system.
  • CI results are historical. The last runs were on 22 October 2026 for RESTful Booker (run #3 (opens in a new tab); by my reading of the job log, no test was retried), 14 September 2026 for Razorpay (run #3 (opens in a new tab)) and 29 August 2026 for Automation Exercise (run #17 (opens in a new tab), with retries on). Each passed when it ran; that says nothing about today. Job logs need a GitHub sign-in.
  • The categories are mine. Another tester could file some of these tests under a different risk.
