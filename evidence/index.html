Defect report: DEF-002

Source: docs/DEFECTS.md (opens in a new tab) in the repository. Order and payment IDs are left out.

Webhook signature validation can never succeed: the global JSON body parser consumes the body before the webhook route

Environment
Express 4.x app (4.22.2 in the lockfile) on Node.js 22.5 or later, with SQLite; Razorpay Test Mode; webhook secret configured. Found on 14 Sep 2026 during real Test Mode execution (Phase 3.3).
Severity / Priority
Severity: High. Priority: not recorded in the repository's defect log.
Component
src/app.js (middleware order) and src/routes/webhooks.js
Status
Resolved 14 Sep 2026 (Phase 3.3.1); last recorded CI run passed on commit da9e7a2

Exact reproduction steps (as recorded)

  1. Compute hmac_sha256(rawBody, RAZORPAY_WEBHOOK_SECRET) exactly as validateWebhookSignature() does.
  2. Send that exact raw body and the correct signature to POST /api/webhooks/razorpay, once with fetch() and once with curl --data-binary using a byte-identical file, to rule out client-side body changes.
  3. Observe the response.
Expected

HTTP 200 with { success: true, message: 'Webhook received and validated' }.

Actual

HTTP 401 Webhook signature validation failed, every time, even with a provably correct signature over the provably correct bytes.

Root cause

app.use(express.json()) was mounted globally before the webhook router. It consumed and parsed the request body, so the route's own express.raw() received an already-parsed object instead of a Buffer. req.body.toString('utf-8') on a plain object returns the literal string "[object Object]", and the HMAC was computed over that instead of the real payload. The comparison was correct; it was hashing the wrong bytes. Fixed by mounting the webhook router before the global parser:

The handler that depends on it, which hashes the raw body and only then parses it:

Impact

No correctly signed webhook could be accepted. It failed safe, not open: a forged webhook could not get through either, so this was a functional defect and not a security hole. It also went unnoticed because the tests that only assert rejection (a 401 was already the expected answer) never exercised the accept path.

Regression tests

New: WEB-FIX-001 (valid signature over the exact raw body is accepted and moves the order from created to paid), WEB-FIX-002 (modified payload with the original signature is rejected and the order is untouched), WEB-FIX-003 (invalid signature rejected), WEB-FIX-004 (duplicate event ID handled idempotently).
Previously failing, now passing: WEB-001, WEB-005, WEB-006, WEB-007. All are in tests/security/webhook-validation.spec.js (opens in a new tab) and run in CI.

Reproduced again on 15 Oct 2026

To check the report rather than repeat it, I cloned the repository at da9e7a2, installed it, and ran the webhook spec with the CI placeholder configuration. With the fix in place, all 11 tests passed. With the fix reverted in a scratch copy (webhook router mounted after express.json(), nothing else changed), 6 of the 11 failed: WEB-001, WEB-005, WEB-006, WEB-007, WEB-FIX-001 and WEB-FIX-004. The five rejection-only tests (WEB-002, WEB-003, WEB-004, WEB-FIX-002, WEB-FIX-003) still passed, which is why the defect hid for so long.
