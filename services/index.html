Payment Workflow Testing

Razorpay Payment Gateway QA & Automation

What was tested
A small Razorpay Test Mode checkout app: order creation, payment signature verification, amount integrity, webhook signature validation and idempotency, refund error handling, and the order state machine.
Why it matters
Payments cross the UI, the app, the gateway and asynchronous webhooks, and each can disagree with the others. Testing found two High-severity defects, both fixed and regression-tested.
Tools
Playwright Test (API and UI), Express, SQLite, GitHub Actions.
What was automated
37 test definitions; 34 run in CI, 3 need live Test Mode credentials and are run manually.
Limitations
Sandbox only. Playwright drove a real Checkout payment in one documented session, but that session is not a committed, repeatable test. No webhook from Razorpay itself was observed arriving, and no successful live refund was completed.

How an Engagement Works

  1. Discuss

    We talk through the application, the requirements and the testing problem you want solved.

  2. Define scope

    We agree what is in scope, what access I need, the timeline and the deliverables.

  3. Execute

    I carry out the agreed testing work.

  4. Report

    I share findings and, if included in scope, verify the fixes.

  5. Hand over

    When automation is in scope, I deliver the code and setup and execution documentation.

Scope is agreed before work begins. If something falls outside it, we discuss it first. It is not added silently.

Before We Start

What I will need from you

  • A description of the application, feature or API to be tested
  • Access to a test or staging environment, not production
  • Requirements or acceptance criteria, if they exist
  • A point of contact for questions and for confirming defects

What I will not promise

  • A bug-free release. Testing reduces risk; it cannot prove defects are absent
  • A fixed number of defects found
  • Turnaround times before the scope is known
  • Coverage of anything outside the agreed scope
