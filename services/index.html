03 Process

How an Engagement Works

  1. Discuss

    We talk through the application, the requirements and the testing problem you want solved.

  2. Define scope

    We agree what is in scope, what access I need, the timeline and the deliverables.

  3. Execute

    I carry out the agreed testing work.

  4. Report

    I share findings and, if included in scope, verify the fixes.

  5. Hand over

    When automation is in scope, I deliver the code and setup and execution documentation.

Scope is agreed before work begins. If something falls outside it, we discuss it first. It is not added silently.

What a defect report looks like

A sample: condensed from DEF-002 in my own Razorpay Test Mode project, not client work. The full report has the code and the regression tests.

Title
Webhook signature validation can never succeed: the global JSON body parser consumes the body before the webhook route
Environment
Express 4.x app on Node.js with SQLite, Razorpay Test Mode, webhook secret configured
Severity
High. Priority not recorded in the repository's defect log.
Steps
  1. Compute the HMAC-SHA256 of the raw body with the webhook secret, as the app's validator does.
  2. Send that exact body and the correct signature to the webhook endpoint, once with fetch() and once with curl --data-binary, to rule out client-side changes.
  3. Observe the response.
Expected
HTTP 200 and a success message.
Actual
HTTP 401, every time, even with a provably correct signature over the correct bytes.
Root cause
The global body parser ran first, so the signature was computed over the string “[object Object]” instead of the real payload.
Impact
No correctly signed webhook could be accepted. It failed safe: a forged webhook could not get through either.
Status
Resolved by mounting the webhook router before the global parser, with regression tests.

05 Expectations

Before We Start

What I will need from you

  • A description of the application, feature or API to be tested
  • Access to a test or staging environment, not production
  • Requirements or acceptance criteria, if they exist
  • A point of contact for questions and for confirming defects

What I will not promise

  • A bug-free release. Testing reduces risk; it cannot prove defects are absent
  • A fixed number of defects found
  • Turnaround times before the scope is known
  • Coverage of anything outside the agreed scope
